The UI shape, the contracts between every piece, and a breakdown into workstreams for implementer agents. Version 0.3 adds file-chip colours, config-field usage links, and range reviews on the full view's map.

Two axes, one grid

Columns show how often code changes. Rows show how much depends on it. Hot code that many things depend on sits top-left, where review starts.

Lanes by role

Infra, config, code, tests and docs each get a band. A lane is marked by its texture, never by colour, because colour is reserved for heat.

One Rust binary

jj-lib at your jj's exact version, tree-sitter packs per language, rusqlite and rmcp. The human and the agent see and change the same state.

Hand-off ready

25 workstreams. Each card copies a brief for an implementer agent, naming its crate, its contracts and the tests that mean it is done.

S2 · Two axes & lanes

Change frequency and connectedness, measured on a reference repo

Before choosing how to show the two axes, I measured them on the reference repo, a private Python/TypeScript project of about 5.6k files whose code is not part of this repository: 399 commits of history, its Python and TypeScript import graph (3,490 files, 18,313 edges), and a role for every one of its 5,670 files. Both jj and the import parsing were read-only, and the op log was unchanged afterwards.

Config is the third-busiest role. Its hottest files are prompt and node YAML, e.g. one prompt.yaml with 17 touches. In the code lane it would sit between code changes and hide them.

Which connectedness measure? Transitive reach looked natural, but it saturates. One import cycle of 270 files (in one core package) lets 26% of code files reach half the code lane, and tests inflate it further. The metric is therefore dependents within two hops, code lane only. It doesn't saturate, still separates the axes, and puts the files you'd expect at the top: the settings module src/config.py, then the event payload and event type modules. Tests are shown as "covered by N tests" instead.

Where config fields are used. Config files keep their own lane. A heuristic links each key to the code that reads it, scored on four things:

  • how specific the read is: get("key") or ["key"] beats a bare string, which beats an attribute;
  • how rare the key is;
  • how close the files are;
  • whether the code mentions that config file at all.

A prototype on the reference repo (docs/analysis/config_fields.py) linked 44% of its 51,709 key paths. In a random sample of 14 links, 12 pointed at plausible readers; the two misses were generic keys read in unrelated code. Look-alike files come in families, the two largest of 237 and 91 files. So links go through one hub per family and key, and a generic loader shows up once instead of 237 times. Grouping by family cuts 143,012 direct links to 27,168 edges through 3,475 hubs. For example, one key of the 91-file family is 91 files feeding 5 read sites.

4Crates ↔ jj: the Vcs trait

B1 provides (jj-lib 0.45.1) · B3–B8 consume

Reads are pinned to one operation and never snapshot anyone's checkout. Writes go through one queue.

preview rewrites and rebases inside a jj-lib transaction, then drops it. Conflict predictions are therefore exact, not heuristic.

The CLI recipes verified in the design session remain the test oracle: every mutation must produce the same trees both ways.

5Core ↔ packs: languages and channels

L1–L5 and P1–P4 provide · B3 B4 consume

The core never names a language or a protocol.

  • A LanguagePack owns its grammar and queries. It hands back language-neutral facts and runs queries for channel rules. It folds key expressions (literals, f-strings, template literals, format!, constants) into a KeyExpr.
  • A ChannelPack owns rule files per language (packs/channels/<protocol>/<lang>-<framework>.toml), plus key normalization and matching.
  • A key with nothing static left becomes a dynamic stub, never a guessed edge.

S6 · Cross-cutting rules

What every implementer must not get wrong

Reads never snapshot

Reads are pinned to an operation. Showing someone's live edits means overlaying files from disk, never snapshotting on their behalf.

Snapshot before you rewrite under someone

Rewriting an ancestor of another workspace's @ without snapshotting it first makes its unsaved files vanish from disk. Verified on jj 0.45.1.

Amend when possible

Edits amend the change they belong to. An immutable target gets a new branch, and range edits are absorbed into the commits that own the lines.

Previews are exact, undo is targeted

The preview is the real rewrite in a dropped transaction. Undo reverts our operation, never "the last one".

Colour means heat

Hue is change frequency, elevation is connectedness, texture is lane. File chips use pastel identity stripes clear of the heat ramp.

Grades are quantiles

Heat by change mass and connectedness by rank, with configurable cut points. Clusters move only when a grade settles.

The core names no language

Only cv-lang-* and cv-channel-* may depend on a grammar or match on a language or protocol. CI enforces it.

Dynamic means dynamic

When a key only exists at runtime, draw an open "?" stub with what is known. Never guess an edge, and never trace at runtime.

Range reviews keep the map

A range view reuses the full view's placement. Diffs sit where their code always sits, and unchanged connected functions start minimized.

Heuristic links show their confidence

Config-field links are scored. Strong ones are drawn solid and thin ones faded with "?", and rate_link overrides either.

Threads follow changes

Anchor to the change id, re-anchor after every op, and mark a thread outdated instead of guessing.

Agents are visible and bound

An MCP session binds to its workspace. Every read emits attention, and every write records actor, workspace and op ids.
